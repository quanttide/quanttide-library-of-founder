# 阿里云 AgentCore 的定位与协作模型

阿里云在云栖大会发布、2026 年 9 月上线文档的智能体构建与治理平台。产品页把它定位为让 Agent 进入生产环境的统一底座；本笔记记录其产品定位、协作对象与任务闭环，并与本仓规格（`docs/specification/work`、`docs/specification/agent`）对照。

## 定位

AgentCore 不自称 Agent 开发框架，而是构建与治理平台。三大能力是构建与运行、协作与治理、观测与评估；概念上分四组：Agent 构建、资产管理、Agent 协作、身份与权限。资源的隔离边界是 Workspace。

它不要求企业统一 Agent 形态：Harness 配置化创建、高代码部署、存量 Agent 纳管，都进入同一套身份、观测、评估与审计体系。公开分享里有一句口径值得记下——平台管理的对象不是 Agent，而是一项任务从构建、执行到验收和改进的完整生命周期，Agent 只是执行单元。

## 协作对象

- Agent：执行单元，绑定模型、Skill、MCP 与凭证，可挂 SubAgent 由自身调度。
- Team：多个 Agent 加人类成员组成的协作单位，设 Team Admin（人类）与 Team Leader（Agent）。
- Leader：理解意图、拆解任务、分派、监控进度、汇总结果；简单任务可直接完成。
- Worker：承担具体工作，任务由 Leader 拆分后分派。
- 任务：围绕一个目标的工作，含内容、团队、状态、协作记录与结果，创建后进入任务房间。
- 子任务：可跨 Worker 拆分，各有状态与依赖关系。
- 评审人：负责验收结果的人或 Agent，与创建者、参与者身份分开计算。

## 三种协作结构

云栖大会的分享按任务性质给出三种结构：即时并发，主 Agent 拆出临时子 Agent 并行探索，结果返回即释放；按需编队，把稳定任务链做成模板，开始时分配能力、权限与上下文，结束回收；长期服务，沉淀为可被发现的数字员工，尚在规划中。

Team 模式是按需编队的落点。Leader 拆解与调度，Worker 执行；团队共享完成任务所需的上下文，任务之间保持隔离；人可以查看 Agent 之间的交流，补充信息、打断执行，或在关键节点审批。

## 任务闭环与验收

任务看板把状态外化为待确认、已创建、执行中、已完成、已取消五列，卡片上的状态标签再区分阻塞、暂停、待验收与失败。正式提交由结果卡片承载，含结果说明与文件；过程文件与结果文件可能同列，验收以结果卡片关联的文件为准。

验收由评审人执行，权限单独判断：有查看或管理权限不等于能验收，团队归属不等于任务可见，上下级任务分别授权。文档明确写了两条：聊天里的认可不能替代卡片上的正式验收操作；外部 IM 的评审人可以给出意见，由执行 Agent 代为处理验收并确认状态更新。

结果会投递回发起任务的会话，包括 App 内聊天与钉钉、飞书等 IM；未配置回复路径时，在任务房间内查看与验收。

## 与本仓规格的对照

| 维度 | AgentCore | 本仓规格 |
|---|---|---|
| 管理对象 | 任务生命周期与 Agent 资产 | 一轮工作的结构，不涉资产与运行时 |
| 交接点 | 结果卡片与任务房间 | 仓库与提交历史 |
| 交付凭证 | 结果卡片关联的文件 | 产物入仓，可按分支、提交与路径追溯（R2） |
| 验收主体 | 评审人，权限独立判断 | reviewer 角色，放行不可委派（R1、R5） |
| 验收代做 | 外部评审人可授权执行 Agent 代为验收 | 明确禁止（R5） |
| 消息与凭证 | 任务聊天与结果卡片并存，正式提交只认卡片 | 消息只传指令与问询，不承载产物（R3） |
| 多团队 | 协调 Agent 兼上级 Worker 与下级 Leader，结果逐级交回 | 转发结构，中间方只传话，判断依据降为转述（R4） |
| 上下文 | 团队内共享任务上下文，任务间隔离 | 两个协作主体各自独立，共享上下文即合并为主体 |

两处差异值得单独说。

共享上下文并不矛盾。AgentCore 让 Leader 与 Worker 共享任务上下文，这两个都在执行侧；评审人是另一身份，不进入执行团队。本仓规格说的两个独立主体，指协作的两方，即执行与放行，不是任意两个 Agent。把这一层写清，两边可以对上。

代做验收是实质冲突。AgentCore 允许外部渠道的评审人给出意见后，由执行 Agent 代为操作验收并确认状态。按本仓规格，这是转发结构，判断依据已经从原件降为转述；更关键的是执行方替放行方签了字。若要采纳这一实践，规格需要显式开例外，并要求留下评审人的原始意见与代做记录，否则账本上「谁放的行」会失真。

## 值得吸收的

- 结果卡片把正式提交与聊天里的文件分开，是 R2 的工程化形态。
- 验收身份独立：查看、管理、验收三种权限分开判断，给了 R1 一个可执行的落地方式。
- 子任务依赖图与事件流是账本的另一种形态，比提交历史更细。
- 按任务性质选协作结构，比笼统地讲多 Agent 更能约束实现。
